# AGENTS.md

Rules for every contributor to Fit-it, human or AI agent. Read this before changing anything.

## Project

Fit-it is a reverse proxy that sits in front of an existing web app and applies per-user Python hooks generated by a coding agent. The original app is never modified.

Documentation lives in [`docs/`](docs/README.md): architecture overview, ADRs, specs (the contracts), epics and the current iteration plan. Read `docs/plan/<current>/00-plan.md` before starting any item.

```
backend/      Fit-it core (FastAPI): proxy, hook runtime, agent, trace seam
demo/         Demo clinic app, the stand-in for a customer app
tests/        unit/ (developer) and acceptance/ (tester)
docs/         Documentation (start at docs/README.md)
.artifacts/   Excalidraw diagrams and project tracking
compose.yaml  Local stack
```

## Running

Everything runs through Docker. Do not create virtualenvs or `.env` files as the documented way to run the project.

```bash
export ANTHROPIC_API_KEY=...        # in your shell, never in a file
docker compose up --build           # core on http://localhost:8000
make check                         # tests in Docker (unit + acceptance)
```

## Secrets

- Secrets come from the host shell through `compose.yaml` (`environment:` passthrough). Never hardcode them, never commit them, never write them to a tracked file.
- `.env` is gitignored. Do not add one to the repo or to the docs.
- If a secret is committed by mistake, rotate it first, then clean the history.

## Branching: Git Flow

| Branch | Purpose | Branches from | Merges into |
|---|---|---|---|
| `main` | Released, demo-ready code. Always green. | | |
| `develop` | Integration branch for the next release. | `main` | `main` (via `release/*`) |
| `feature/<short-name>` | One feature or change. | `develop` | `develop` |
| `release/<version>` | Stabilize a release; only fixes. | `develop` | `main` and `develop` |
| `hotfix/<short-name>` | Urgent fix on released code. | `main` | `main` and `develop` |

- Never commit directly to `main` or `develop`. Every change goes through a pull request.
- Branch names are lowercase kebab-case: `feature/hook-runner`, `hotfix/guard-bypass`.
- Tag every merge into `main` with a semantic version: `v0.1.0`.
- Delete feature branches after merging.

## Commits: Conventional Commits

Format: `<type>(<scope>): <summary>`

- Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `build`, `perf`.
- Scopes: `core`, `guard`, `agent`, `proxy`, `widget`, `docker`, `docs`.
- Summary in English, imperative mood, lowercase, no trailing period, 72 characters max.
- One logical change per commit. Breaking changes add `!` after the scope and a `BREAKING CHANGE:` footer.

Examples:

```
feat(proxy): forward requests to the base app
fix(guard): reject dunder attribute access
docs: add architecture diagram for the API-only flow
```

## Pull requests

- Target `develop` (or `main` only for `release/*` and `hotfix/*`).
- Title follows the Conventional Commits format.
- Description says what changed, why, and how it was verified.
- Merge only when the self-check passes and one other contributor has reviewed it.
- Squash-merge feature branches so `develop` keeps one commit per feature.

## Code rules

- Simplest working solution first. No abstractions, config or files "for later".
- Reuse what is already in the repo before writing new code; standard library before new dependencies.
- Non-trivial logic ships with a runnable check (a unit test in `tests/unit/`).
- Security is never simplified away: generated hooks always pass the AST guard, run fail-closed, and only reach the client app through its API with the user's own session.
- Code, comments, commits and docs in English.

## Agent roles

Per [ADR 0013](docs/adr/0013-developer-and-tester-agents.md), each item of an iteration plan goes to:

| Role | Does | Never |
|---|---|---|
| **Developer** | Implements one item on `feature/<id>-<slug>` from `develop`, with unit tests in `tests/unit/`, runs `make check`, opens a PR into `develop` | Edits `tests/acceptance/` or a spec |
| **Tester** | Writes acceptance tests in `tests/acceptance/` from `docs/plan/<current>/requirements.md`, `contracts.md` and `docs/specs/` only, one or more per `REQ-*` id (named after it), runs them on the developer's branch, reports pass/fail per requirement | Reads `backend/`, `demo/`, `tests/unit/` or the developer's branch |
| **Reviewer** | Only when an acceptance test fails: reads requirement, spec, test and code, and rules **code wrong** (developer fixes), **test wrong** (tester fixes) or **spec wrong** (proposes a spec change for a human to approve). Writes the ruling in the PR. Escalates to a human after two rounds. | Writes code or tests itself |

A human merges when every requirement of the item passes, and ticks `docs/advance/checklist-<NN>.md`.

## Agents

- Do not commit, push, merge or tag unless a human asks for it in the current task.
- Do not delete files or branches, or rewrite history, without explicit approval.
- Keep diffs scoped to the task. Do not reformat or refactor unrelated code.
